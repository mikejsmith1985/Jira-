# Quickstart: Issue Author

How to prove this feature works, against the real instance, without reading the code.

## Before you start

- Jira+ running, and either the relay bookmarklet clicked on a Jira tab or a token saved.
- A project you can create issues in.
- An existing issue you are willing to edit — a stub is ideal.
- Microsoft Copilot open in a browser tab.

## Scenario 1 — Write a new issue from scattered material

Proves User Story 1 and SC-001.

1. Open **Author**. Confirm it says a **new issue** will be created.
2. Paste any paragraph of text, label it, and add it. Confirm it appears as a card with that label.
3. Add a second source.
4. In "your own words", write two sentences about what you want.
5. Choose a project. Confirm the issue types offered are that project's real types.
6. Choose an issue type. Confirm the fields shown are that type's real fields, and that required
   ones are identified as required.
7. Build the prompt. **Read it.** Confirm it contains both sources, your own words, the nine section
   headings, and only field identifiers from step 6.
8. Copy it into Copilot. Paste the reply back and read it.
9. Confirm proposed values appear in the draft and **nothing has been written to Jira**.
10. Change the summary by hand, to prove the proposal is a draft and not a decision.
11. Create. Confirm the diff lists every field first.
12. Confirm one issue exists in Jira with the right type and the right values.
13. Confirm the draft is now empty.

**Expected**: one issue, correctly typed, required fields populated, drafted content present.

## Scenario 2 — Enrich a stub without creating a duplicate

Proves User Story 2, SC-002 and SC-003. **This is the one that must not fail.**

1. Enter the key of your existing stub. Confirm the screen now says it will **update that issue**
   and will not create a second one.
2. Confirm the draft filled from the issue's real values.
3. Save without changing anything. Confirm it is **blocked**, and the reason is that nothing has
   changed.
4. Change only the acceptance criteria.
5. Save. Confirm the diff lists **only** acceptance criteria.
6. In Jira, confirm the description is **byte-identical** to what it was. This is the check that
   catches a description silently rewritten by normalisation.
7. Search Jira for issues created in the last five minutes. Confirm **none**.

**Expected**: the stub is updated, one field was written, nothing else changed, no issue was created.

## Scenario 3 — A reply that is wrong in four ways

Proves the edge cases, FR-026 to FR-029, and SC-004. Do this by editing the reply by hand before
pasting it; you are testing the parser, not Copilot.

| Edit the reply to… | Expect |
|---|---|
| Change the pack identifier | The whole reply is rejected, and says why |
| Add a field id like `customfield_99999` | Dropped and named, never sent |
| Put an invented value in a list field | Becomes no value, and is named |
| Add a line of prose where an item belongs | Counted as unparsed and shown |
| Include "generated by AI" in the description | The phrase is gone from the draft |
| Omit three sections | All nine present, the three marked as needing validation |

**Expected**: the draft is unchanged except where a proposal was valid, and every rejection is
visible rather than silent.

## Scenario 4 — Change the template

Proves User Story 4 and SC-005.

1. In Setup, add a tenth section with a line of guidance.
2. Build a prompt. Confirm the tenth section is asked for, in the position you put it.
3. Remove every section. Build a prompt. Confirm it asks for a description with no imposed
   structure.
4. Restore the nine.

**Expected**: no restart, no new version, no code change.

## Scenario 5 — The draft survives

Proves FR-008 and SC-006.

1. Half-write a draft with two sources.
2. Reload the page. Confirm it is intact.
3. Stop Jira+ from Setup, start it again, reopen. Confirm it is intact.
4. Click the relay bookmarklet, which navigates you away, and come back. Confirm it is intact.

**Expected**: intact three times.

## Scenario 6 — With no token at all

Proves the feature inherits the relay.

1. Remove the stored token in Setup, if you have one.
2. Confirm the relay is connected.
3. Run Scenario 1 from step 5.

**Expected**: identical behaviour. Authoring adds no authentication of its own.

## What failure looks like

If any of these happen, the feature is not done:

- A second issue appears while enriching.
- A field is written that the diff did not list.
- A field identifier appears in a prompt that the create screen does not offer.
- A readiness finding blocks a write.
- A blocking condition is presented as advice.
- A draft is lost by reloading, restarting, or clicking the bookmarklet.
